# 微信、QQ、抖音统一聊天采集规则

## 来源、范围与状态

- 来源：2026-09-17 用户要求所有App的采集内容、频率、去重原则一致，各App仅做必要适配；首次打开聊天短暂看一眼也要采集，不能被2秒门槛挡住。抖音修好后继续增加QQ采集，取代本轮“QQ采集暂缓”的排期。
- 本文是统一需求、现状核查和实现验收清单，不是已完成证明。此前39项测试通过仅覆盖旧限频补丁及已有链路，不代表本规则已经实现。
- 继续沿用用户操作真机、助手只读诊断的约定。后台按App分Tab。GIF发送保真属于另一条任务，不以截图采集代替。

## 一、各App共用规则

### 1. 采什么

- 以微信现有完整能力为基线：前台聊天可见区域截图、会话分组、通知中实际可读内容/资源、可靠的截图补偿、持久化与断网补传。不是仅采通知。
- 聊天截图覆盖当时可见的文字、图片、表情、语音/视频/文件卡片以及已显示的语音转文字。卡片截图不能冒充原始音视频/文件已采集；不自动播放、转写、打开附件或翻页。
- 排除输入草稿、输入法键盘、系统状态栏等非聊天内容；标题用于会话识别。剪裁不能截断当前可见的最后一条消息。
- 仅采用户开启功能后允许采集的页面；联系人列表、搜索、评论、直播、桌面、其他App等不得套用聊天裁剪规则。
- 通知内容与聊天截图是不同来源证据，不能仅因同文便误删不同时间发送的两条真实消息。来源合并须有可靠关联，不能猜测。

### 2. 何时采集：首次与变化优先，而非定时轮询

| 场景 | 统一目标 |
|---|---|
| 首次识别到有效聊天页 | 立即请求首采，不人为等待2秒；页面尚未渲染到可识别状态时，仅做有界重试 |
| A切换B，或退出后重新进入 | 按新的一次进入处理，不继承其他会话的冷却；最终内容与历史相同则不重复入库 |
| 停留不动、消息内容未变化 | 不周期截图，不因时间到达而重复上传 |
| 收到/发出新消息、语音转文字出现 | 触发变化采集；不能用固定冷却直接吞掉新内容，密集同一更新事件可合并 |
| 普通重复UI事件 | 合并事件、同一时刻最多一个截图任务，保留仍有必要的末次变化 |
| 只输入草稿、光标闪烁、状态动画 | 不视为新聊天内容；也不能让输入行为取消尚未完成的新消息采集 |
| 键盘展开/收起 | 更新裁剪区域；若没有新增可见内容，不新增重复记录；若显露未采内容则保留 |
| GIF/视频预览逐帧变化 | 不按每一帧生成新聊天记录；不能只凭截图SHA变化判定新消息 |
| 向上翻阅历史 | 已向用户询问；建议滚动停稳后采新增视口，重复历史内容去重，尚未将此建议当已确认规则 |
| 离开聊天/关闭采集 | 取消尚未执行的旧页面任务，不截图下一页面；已实际截取并确认归属的有效图仍可完成持久化，不因离开而丢掉 |

“2秒”不再作为首次打开或新会话的强制等待，也不作为全局一刀切的采集门槛。如需对重复候选做资源保护，应放在共用策略层，首采、真实变化与补偿规则统一定义，不能各App私自设置。

系统截图是异步且受权限/系统限流约束；实现应消除人工等待并记录失败原因，不能承诺尚未渲染或系统拒绝时也100%取得图像。

### 3. 去重分层

1. 事件层：合并同一变化的多个事件，避免并发/排队重复截图；无变化不轮询。
2. 内容层：按App、用户/账号、会话隔离。相同已采内容跨返回、重复通知补偿、重启和上传重试不能不断新增。
3. 图片层：完全相同资源使用SHA复用；SHA不同不必然代表新聊天内容。键盘裁剪、空白变化、动画帧等需结合实际内容区域和消息变化判断。
4. 持久化层：去重与入队原子化。截图失败、资源未保存不能提前标记“已采”；失败后允许重试。
5. 上传层：重试复用同一记录身份与资源，不因网络失败制造新消息；不同会话不能因图像相同合并会话关系。

不得直接用整图感知哈希/相似度阈值吞掉“只有几个字变化”的新消息。无法可靠判断时保留候选并暴露诊断，不宣称语义去重已解决；实现前必须有动画重复与微小新增文字的成对回归。

### 4. 全部入口归一

- 无障碍聊天事件、输入法发送后的前台刷新、通知触发截图、空树/OCR补偿都必须进入共用的截图调度/去重策略；App适配器不得旁路另建定时截图循环。
- 通知中的文字/已有媒体可直接入队，不要求人为等待截图时间；通知需要截图时必须核对当前前台确实是目标聊天。只有App包名相同不足以证明会话相同。
- 空树是适配能力差异，不是放宽非聊天页采集的理由。身份不可靠时明确标记未识别或跳过，不能猜标题混入已识别会话。
- 上传重试退避与采集频率是两件事：继续共用队列、资源先于消息、重试幂等和用户隔离。

## 二、各App只允许保留的差异

- 包名、真实聊天页判据、页面树结构、标题/账号/会话标识获取、聊天正文/输入框边界、消息变化信号和系统截图能力。
- 微信保留经验证的空树识别/OCR能力，接入统一策略，不机械复制微信点击文案到QQ/抖音。
- 抖音40.5.0已有前景容器/标题/输入区取证，仍需快速进退、新消息、动画重复及负例验收。
- QQ9.3.60已有聊天输入/标题/设置控件取证；补非聊天负例、输入区显隐和会话切换后接入相同核心，不能只加通知白名单。
- 同名会话/账号切换不能仅靠标题假装已有唯一身份；现有本地账号键与可见标题分组的限制必须保留在验收报告。

## 三、源码现状与差距（2026-09-17核查）

| 入口/模块 | 当前事实 | 差距 |
|---|---|---|
| 主视口 ViewportDebouncer | 300ms稳定等待，上一版另加全实例2000ms最小间隔 | 不是按会话的首次立即采；持续事件可能推迟首采，需改共用策略 |
| 无障碍事件过滤 | 忽略滚动、EditText文字变化；部分点击按微信文案识别 | 首进/退出状态未统一建模，跨App事件适配需明确 |
| 输入法发送刷新 | 700ms延迟后再走主视口 | 应成为共用变化触发入口，不独立决定全局规则 |
| 微信空树 | 700ms或语音转字1500/6000ms任务；独立last SHA | 绕过主限频；去重作用域及补偿与首采关系未统一 |
| 通知截图补偿 | 1200ms防抖、失败5000ms重试；独立队列/互斥/SHA | 与前台截图并行，需共用；会话归属不能只验证包名 |
| 通知监听 | 三App均支持；文本/资源和需补偿分支 | 不是QQ完整聊天页采集的替代品 |
| CaptureCoordinator / Room | 会话消息指纹、SHA资源、原子已见/待上传队列 | 精确图片去重已有，不能解决动画换帧/视口大小语义重复 |
| CaptureUploader | 共用资源与消息队列；30s/120s/600s/1800s失败退避 | 重试频率不是截图频率；不能为降频破坏补传 |
| AdapterRegistry | 微信、抖音聊天页；QQ未注册 | QQ完整截图仍需实现 |

## 四、实施顺序与验收矩阵

1. 用失败测试证明首次进入不等待、A→B不被A冷却、重复事件不重复采、离开取消旧任务、新消息末次保留。实现共用进入/变化/退出调度，而非继续给单个App打补丁。
2. 将所有截图来源接入同一决策入口；对重复候选/失败重试/已捕获后离开明确生命周期，保持现有通知、空树能力不退化。
3. 内容去重补齐完全相同、键盘显隐、同一GIF换帧、少量新增文字、相同内容真实重复发送、不同会话相同图片等成对测试。未通过不得宣称“无重复且无漏采”。
4. 先完成抖音实机快速进入后退出、停留不动、新收发、切会话；再以QQ现场结构新增适配器并复用全部核心测试。
5. 微信、QQ、抖音同一验收表逐项标注：单测/夹具/真机/未验证，不能用其中一个App通过代替其他App。包括离线补传、重启、权限关闭、负例页面、后台分Tab。
6. 构建、独立审查、用户真机操作；保留其他任务改动。未重新安装和真机验收前，不把代码状态写成手机已生效。

## 五、本轮实施进展（不代表统一完成）

- 主视口新增按稳定会话key区分的首采模式：首次、同窗口切会话直接触发，退出后重入重置；旧全实例2秒配置取消，同会话后续事件仍合并。新增2项回归先失败，再与既有采集用例通过；通知补偿的原防抖默认保持不变。
- 非支持App成为活动窗口、明确非聊天页或关闭采集时撤销主视口待执行任务；输入法窗口不误当退出。截图前仍重新确认会话，避免等待期间切换导致串图。
- QQ依据已有9.3.60脱敏真机树补页面、标题、输入工具栏、键盘显隐、身份校验和拒绝歧义测试；当前正在红绿实现。不把QQ夹具回放写成QQ真机验收完成。
- 仍待：通知/空树与主视口统一决策、动画帧及键盘显隐内容级去重、真实新消息采集与快速进退验收、全App矩阵。因此主视口首采补丁不是全部统一需求完成。

## 六、用户确认分工：采集整理暂停，优先GIF发送

2026-09-17 用户说明另一个会话负责聊天文字识别，要求本会话先整理采集待改点，转而修复GIF发送。本会话不再修改采集相关实现，不撤销已有未提交改动，不覆盖另一个会话的OCR/身份识别工作。

待继续时逐项执行：
1. 复核主视口首次进入/切会话/离开重进的实际事件接线，包含XML订阅变化；最新Robolectric配置验证尚未完整通过，不能按代码审查冒充实机通过。
2. 将无障碍事件、输入法发送后刷新、微信空树、通知补偿接入共用调度，去掉入口之间互相绕过的重复任务；识别渲染未完成与无变化，不靠固定轮询。
3. 共用去重覆盖：完全相同图片、键盘显隐、动画帧、微小新文字、真实重复发送、跨会话相同图；成功落盘才记已见，失败可重试，避免与OCR会话识别结果冲突。

## 七、用户恢复采集实施：手机断连后继续离线开发

2026-09-17 用户最新指示：原始 GIF 与 AI 合成 GIF 发送处理后，继续三 App 采集；手机将拔掉。本节取代第六节的暂停排期，不取代其保护外部文字识别改动的边界。

本次最小实施顺序：
1. 真实模板合成产物进入真实发送器及 FileProvider URI，检查 GIF 字节、多帧及 MIME，不能只分别测试 renderer 和 mock sender。
2. 共用 `WindowMediaCapturer` 保证所有入口同一时刻只有一个物理截图请求；取消中的系统截图须等回调后释放，避免立即放行另一个请求。锁不覆盖 OCR 身份确认的 800ms 等待及数据库上传。
3. 主视口和补偿共用的防抖补上有界等待，持续变化保留最新候选，不无限重置 300ms 定时器；首进入仍立即。
4. 重跑三 App 适配、配置、共享采集/去重/持久化与 GIF 定向回归，再构建；保留另一会话新增 `titleBounds`、身份确认与截图窗口校验。

注意：截图互斥不等于三路语义请求合并；完全相同 SHA 去重不等于 GIF 动画帧/键盘裁剪语义去重。此两项仍需单独实现验证，不能按互斥测试通过宣布全部完成。断连后不要求用户立刻重连，不安装、不自动发送，真机矩阵保持待验收。

### 共享调度本次红绿与审查

- 新增三入口并发截图、取消后仍等待物理回调、持续事件不无限推迟末次候选3项测试，首次运行16项中3项按预期失败；实现共享截图互斥和最长1200ms候选合并窗口后，三App适配/协调器/XML等61项通过。
- 1200ms是持续变化的最大合并等待，不是首次进入的等待、不是固定采集周期，也不是内容去重窗口。该默认行为同时作用于主视口和通知补偿；没有新事件不会周期截图。
- 独立审查发现编码调度边界取消可能泄漏原始Bitmap。新增调度前取消回归，并补“排队期间关闭采集后不再发起截图”的回归，8项中2项按预期失败。现将原图释放移到包围整个编码调度的finally，锁内重查取消与采集授权，待最终扩大回归确认。
- 共用锁范围为系统截图及本地裁剪/落盘，不含OCR、身份确认延迟、入库和上传。系统请求已提交后不能主动撤销，取消等待回调只用于收尾；回调不返回时当前没有另行编造成功或放行并发请求。
- 对方会话已把QQ的 `titleBounds` 接入统一标题证据。保留其主视口身份确认重拍、pending→confirmed持久化及整屏/窗口截图回调校验，未改文字/OCR算法。

### 尚未满足的项目（不以通过单测代替）
