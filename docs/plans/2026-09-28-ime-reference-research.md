# 搜狗及开源输入法参考研究与验证顺序

> 2026-09-28 用户要求继续研究，学习搜狗和公开实现。后续实现沿用 superpowers:executing-plans；本轮是资料研究与隔离评测校正，不代表已选定可交付引擎。

**Goal:** 找到可生成自然短句、保留个人习惯且满足手机逐键性能的方案。

**Architecture:** 优先研究保留现有输入状态与两套习惯数据，改进原生候选生成及统一评分。先验证轻量统计解码，必要时再研究小模型重排；不把来源不同、量纲不同的分数直接相加。

**Tech Stack:** 现有定制 Rime/JNI、libime/KenLM 参考实现、原生附加模块隔离探针。当前分支工作，不更换手机安装包。

## 搜狗公开资料能证明什么

- 搜狗官方 2014 年 iPhone SDK 文档记载九键输入、上下文调频、自造词记忆、人名场景感知及云输入。这说明其能力不止词表收录；但历史功能文档不能证明当前 Android 内部模型、评分公式或离线命中率。[官方文档](https://dl.pinyin.sogou.com/wapdl/ios/sdk/sogou_iPhone_sdk_20140616.pdf)
- 官方更新日志分别记录音节切分、全简拼混输、上下文调频、学词与性能改进，2026-06-26 仍有打字模型更新。没有找到足以复现现版本完整解码器和训练模型的官方开放资料。[更新日志](https://pinyin.sogou.com/changelog.php)
- 对妙言的启示是分别验收拼写匹配、组句、排序、学习、耗时。不能推断用户截图里的搜狗结果一定来自云端，也不能声称照搬某个公开模型就等于搜狗。

## 可落地参考

### libime：完整候选图、统一概率和独立历史

作者介绍了拼音切分图、词典匹配、语言模型评分和多结果搜索。整词与多词路径共同参与搜索，和当前“有完整词就不组句”的开关不同。[作者说明（一）](https://www.csslayer.info/wordpress/fcitx-dev/libime-intro-1/)

源码固定到 `171edcf137001e8eb8274f53ec010058cda70b09`，本机副本及 URL 清单在 `engine-eval/research/libime-sources.json`：

- `decoder.cpp`：词典构建 lattice，前向评分、反向求多结果；有搜索宽度、每段节点数和回溯上限，避免穷举。[源码](https://github.com/fcitx/libime/blob/171edcf137001e8eb8274f53ec010058cda70b09/src/libime/core/decoder.cpp)
- `pinyincontext.cpp`：更新切分图时复用有效节点；取消已选词时清理失效状态；使用上下文和已选词形成后续评分状态。[源码](https://github.com/fcitx/libime/blob/171edcf137001e8eb8274f53ec010058cda70b09/src/libime/pinyin/pinyincontext.cpp)
- `userlanguagemodel.cpp`：系统模型与历史模型分开保存，概率融合后还保留系统分数下限。历史模型不等于替换公共词库。[源码](https://github.com/fcitx/libime/blob/171edcf137001e8eb8274f53ec010058cda70b09/src/libime/core/userlanguagemodel.cpp)
- 作者使用分层历史池体现近期与长期差异；这支持“通用模型与个人偏好分离”的方向，但不应把妙言已建立的 24 小时最近优先和 14 天衰减强行换成另一套规则。[作者说明（二）](https://www.csslayer.info/wordpress/fcitx-dev/libime-intro-2/)

这套结构值得优先复现。读源码不等于已验证其中文九键效果；需使用真实 C++ 实现与配套模型，而非只运行近似脚本。

### Gboard：借鉴有限搜索与小模型接入，不能照搬性能结论

Google 的 2024 年论文把神经模型输出接入既有搜索图，并用剪枝和紧凑结构控制开销。在线实验采用约 640 万参数的单层 LSTM，仍报告约 17%–28% 的解码延迟增加；实验语言不含中文。因此它支持保留成熟输入框架的方向，却不能证明妙言换模型后不会变慢。[原论文](https://arxiv.org/html/2410.15575v1)

### PinyinGPT：拼音约束有参考价值，当前不能直接移植作逐键引擎

ACL 2022 工作把候选限制在合法读音内，讨论上下文和同音辨别。但论文假设已知正确切分，未完成全拼/简拼混输；示例配置在 V100 上的 6/12 层推理约 94/145 ms，不是 Android 逐键耗时。不能用其准确率替代本项目九键、混拼和手机性能验收。[论文](https://aclanthology.org/2022.acl-long.133.pdf)

## 校正上一轮 libime 原型的证据边界

原型 `engine-eval/libime/evaluate.py` 仅接受三列制表符记录；官方 `loadTextImpl` 接受空白分隔的两列/三列，缺省 cost 为 0。因此原型读取了 204,968 行，漏掉 95,266 行合法记录，不能当作官方 libime 引擎结果。[官方读取实现](https://github.com/fcitx/libime/blob/171edcf137001e8eb8274f53ec010058cda70b09/src/libime/pinyin/pinyindictionary.cpp)

本次新增隔离副本 `evaluate-parse-fixed.py`：

- 三条格式夹具中，旧读取仅保留“你好”，修正后“阿阿 / 奥姆 / 你好”全部保留，证据 `parser-check.json`。
- 同一份词典的 300,234 行均符合两列/三列格式。仅修正读取，其余搜索与分数保持不变，重新解析模型子集，避免沿用旧缓存。
- 原 28 行复现矩阵首位命中由 25 行变为 24 行，数字码“等你懂了”变为“的明洞了”；“煮的面”仍非首选。该小样本数不是总体准确率。
- 输出为 `results-parse-fixed.json/.log`。它仍是 Python 近似搜索，未实现真实 KenLM 状态、未知词处理、libime 分段图和候选策略；不得据此淘汰整个 libime 路线。

## 方案取舍

| 路线 | 当前决定 | 原因 |
| --- | --- | --- |
| 再扩大 Rime beam / 无条件把组句放前面 | 不继续作为修复方案 | 已复现耗时扩大及“冷静 / 充电宝”退步 |
| 轻量统计语言模型 + 同图比较整词与短句 | 第一优先验证 | 有完整开源参考，容易限定工作量和分析错因 |
| 小模型对少量已生成候选重排 | 后备实验 | 只能改善排序，不能补救目标未生成；还需模型来源与真机预算 |
| 每键调用云模型或直接大模型生成 | 不进入当前实现 | 不能满足本次离线快速响应与现有状态兼容要求 |
| 全盘替换引擎及用户库 | 不进入当前实现 | 尚无原生 userdb 与既有交互迁移证据 |

## 下一阶段执行顺序和停止条件

1. **建立可信参考基线。** 固定 libime 源码、配套数据与编译选项，直接运行其 C++ 解码器。先测锁音，核对词典行数、未知词和边界状态；数字码适配单独标注，不能把输入预先选成正确拼音后声称九键成功。与 28 行、历史 291 行语料分别对照，报告目标生成率、首位/前五与新增错误。
2. **判断模型还是搜索导致失败。** 记录目标路径在哪一步丢失；目标路径存在却分数较低时，先检查语料和评分。不得继续靠扩大 beam 或增加反馈答案调参。另建日常口语、专名、混拼留出集，保持答案不进入训练或人工词表。
3. **验证附加原生路径。** 只在隔离 userdir 接入，保留原生候选索引、读音和消耗按键范围。通过部分选词、锁音、退格、撤销、重启学习后，才考虑正式 JNI。原生扩展还有跨库 RTTI 问题，不能只凭已有提交探针通过就启用。
4. **再处理应用层排序。** 只有生成结果合格后，修改 `OfflineT9Candidates.kt` 中公共词收录阻断整句的规则。公共收录作为候选资格，不自动等于常用优先；个人词、真实选词及 preferred 的现有约定单独保留。跨来源分数先校准，不能直接拼列表或硬加分。
5. **分别验收习惯与性能。** `DecoderHabitContractTest` 保护应用层，另补原生 userdb 的旧数据读入、选择、撤销及重启测试。增量缓存需覆盖输入串、锁音、已选前缀、上下文和词库/习惯版本；失效时正确重算，不能返回旧会话结果。模型加载离开逐键路径，在同一实体手机比较冷/热 p50、p95、p99、最慢值与内存，再测完整按键到显示时间。

上述是下一阶段研究顺序，不是新引擎性能承诺。已有候选退步、习惯丢失或耗时超过实测预算时，保留旧实现，不发布该实验版本。
