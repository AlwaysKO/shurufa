# 2026-09-22 聊天标题真机诊断

## 授权与执行边界
- 用户明确提供“王彦兵”为正确名称，并允许安装独立无联网权限诊断应用；另一样本是画面可核对的“文件传输助手”。
- 荣耀 ELI-AN00，Android API 36，4096 字节内存页。正式输入法 `com.yuyan.pinyin.offline.debug` 仍是 20260922.09 / 2026092209，未覆盖安装、卸载、清数据或改动正式识别实现；未发送消息、未执行正文 OCR。
- 独立包 `com.yuyan.ocrprobe`，minSdk 30（诊断压缩使用 WEBP_LOSSY）；不改变主应用 API 23。构建后实际检查合并 APK 没有 INTERNET 权限、固定原证书 SHA256 匹配、复制哈希一致；安装及结束测试后的 force-stop 均只针对诊断包。
- 实验源代码、截图、原始 JSON、脚本均位于本地 Git 忽略目录 `artifacts/diagnostics/2026-09-22-title-ocr/`；照片不提交。两张输入只取顶部 270 像素，已排除聊天正文。

## 方法与可复现性
- 三个引擎逐一 force-stop 后冷启动，核对原始报告 PID，进程级 RunGate 防止 Activity 重建重复启动推理；方向固定。纯 JVM 5 项测试通过，包含先红后绿的并发门禁验证；只读审查的配置重建问题已修复。
- 每引擎：2 张图 × 2 种输入（原始 / 顶部 WebP82）× 2 种高度（216 / 完整 270）× 3 次，共 24 次。重复同图不是独立样本，不能据此发布整体准确率、可靠 P95 或微信姓名覆盖率。
- “顶部 WebP82”是在 Android 对同一张 270 高度顶部图压缩后再裁切，不是完整屏幕压缩的精确复刻。不能把结果直接等同于旧 APK 的全屏压缩基线。
- 选行规则复制当前正式实现，不根据已知正确答案挑选或修正 OCR。逐次保存所有原始文字/框、选中标题、精确匹配结果与耗时。
- PSS 仅在创建前、创建后、每次识别完成后和释放后采样。下表是**完成后采样最大值**，不是推理绝对峰值，也不是正式输入法整体内存或严格引擎独占内存。样本少、启动基线不同、包含 GC/共享库和诊断程序开销。
- `create_ms` 只称引擎创建耗时：ML Kit 可能在第一次 process 惰性加载；Paddle 在 create 加载 ONNX。不能直接将二者当作等价模型冷加载。

## 核心发现：王彦兵
1. 当前原始 216 高度输入，ML Kit 原始文字其实是 `王彦兵`，框 `[518,168,666,221]`；现有 `line.bottom <= headerHeight` 将它丢掉，随后选中状态栏 `09:49 ◆e`。三个重复均如此。
2. 完整 270 高度输入可保留标题，但 ML Kit 输出为 `王彥兵`，框 `[520,174,668,222]`；`彥` 与用户给定 `彦` 不同，按整行逐字验收不算正确。
3. 顶部 WebP82 + 216 高度在这个样本中返回 `王彦兵` 且框底恰为 216，被正确选中。不能推导压缩一定有害或原始像素一定更准；此前输入优化的像素测试并不能证明真实识别收益，边界/选行缺陷会改变最终结果。
4. small/tiny 在两种高度、两种输入下均正确输出 `王彦兵`。
5. 因此已定位两个不同层次的问题：裁切/框过滤导致错选状态栏；完整输入仍存在中文繁简字形差异。不把姓名硬编码进纠错表，不用模糊姓名合并掩盖错误。

## Paddle 部署实证
- 固定 SDK revision 与模型 SHA256 见 `2026-09-21-title-ocr.md`，ONNX Runtime 1.21.1，CPU 4 线程，默认 PaddleOCRConfig。
- 官方示例的 `com.quickbirdstudios:opencv:4.5.3` 在本机 API 36 上加载失败，真实错误为 `dlopen failed: cannot locate symbol "__sfp_handle_exceptions" ... libopencv_java4.so`。初始失败 JSON 保留为 `initial-report-small.json` / `initial-report-tiny.json`，不当作推理结果。
- 仅诊断应用改用 OpenCV 团队 Maven AAR `org.opencv:opencv:4.12.0` 后三个引擎成功执行。来源说明：[OpenCV 官方 Android 集成说明](https://opencv.org/opencv4android-usage-models/)。正式 APK 未新增 OpenCV/ONNX 依赖。
- small/tiny 的 PSS 随迭代上升后又下降；本轮不能仅凭这种走势认定永久泄漏。需要继续隔离临时数组/Mat/ORT工作区与 GC 行为后，才能声称经过内存优化。

## 建议与未完成项
- 先修复正式链路的标题区域与状态栏排除：应依据实际页面/状态栏/工具栏边界，不简单放宽到正文，也不仅删除 bottom 校验放行越界框。需新增这次框越界却被状态栏抢占的回归。
- 若比较模型，tiny 在这两例中与 small 一样正确、更快、内存更低，因此比 small 更值得下一步验证；但**当前整套检测+识别 SDK 实测并不比 ML Kit 省内存**，不直接替换。
- 可评估只针对已定位标题行运行识别模型、减少完整检测流程及临时内存；此项未实现/未测，不能称为已达成准确且省内存。
- 还需更多用户标注标题、群人数/Emoji/生僻字/深浅色，以及会话误归属和持续采集回归。本轮未测首图持久化、多帧稳定器的完整端到端准确率。
- 独立诊断已结束并停止进程，诊断应用保留供后续测试；未自动卸载。正式代码/输入法包没有在本轮被修改。
