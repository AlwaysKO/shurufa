## 缺陷分层

1. **底层没有生成目标。** 数字码和锁音两条路径都能复现“煮的面”缺失。只在结果列表重排或拉更多页无法产生不存在的候选。
2. **公共收录被当作优先依据。** `OfflineT9Candidates.kt` 的 `hasDictionaryWhole` 包括 `publicPhrases.contains`，会关闭 `allowNativeWhole`；`publicWhole` 又排在 `nativeSentences` 前。公共索引只有收录信息，不能证明词是日常高频搭配。“朱逢博”在公共索引内，“煮的面”不在。解除这道门也无法单独解决底层缺失。
3. **锁音路径能力不同。** `RimeEngine.kt` 中无 unlocked digits 的 T9 组合调用 `rankNative`，只能重排已有原生候选，不能生成短句。直接塞入 `nativeIndex == null` 的本地候选会进入 `reset()` 提交路径；未核对已选前缀前不能这样补救。

上游对应版本的 `ScriptTranslation::Evaluate` 仅在没有完整精确词条时调用 `MakeSentence`，且持有一个 `sentence_`；`Poet` 返回一条最佳组合。无 grammar 时使用动态规划，有 grammar 时才使用带上下文评分的搜索。这为观察到的现象提供机制解释，但项目使用定制预编译库，不能把上游源码当作已逐行核对的定制实现。

- 上游源码：https://github.com/rime/librime/blob/1.11.2/src/rime/gear/script_translator.cc
- 上游源码：https://github.com/rime/librime/blob/1.11.2/src/rime/gear/poet.cc

现有 T9 内嵌方案没有已配置语言模型的证据；有 Grammar 接口或版本号不等于模型已启用。此前将问题主要解释为“日用词库不足”不完整，后续不得以补几个词作为整体修复结论。

#### 收窄实验结果：未通过，已撤回生产修改

先运行 `DefaultCandidateQualityTest`，冷门公开词抢先和未知整句抢先两项按预期失败，真实姓名学习和“煮的面”一次分段学习两项通过。加入推荐/展开分层后运行 184 项回归，3 项失败：

- 空历史 `96353`：“我饿了”被降到“我”后。来源是否在核心库不能准确区分日常短句和冷门词。
- 长句逐键回放 `9628924`：“我不再”被挤到第 98 项，破坏既有分段可用性。
- 刻意缩小词库的测试中，“总额而”从第一位移到“总额”“用”之后。此项符合新目标，但前两项属于不可接受的连带影响；没有通过改写旧测试掩盖。

独立审查另外指出：原生 userdb 已学而应用 SQLite 未保存的词无法通过当前 `text/comment` 接口识别；直接使用应用库作为推荐资格，会改变这部分旧习惯。界面推荐边界每次扫描全列表也需要改成缓存后再评估，不能只测排序耗时。

所有实验生产修改及候选栏测试已归档 `engine-eval/quality-prototype/` 并撤回。正式 Kotlin/JNI/词库均无 diff；不构建、不安装不合格的修复 APK。失败日志：`quality-red.log`、`quality-green.log`；不是手机 UI 验收。

保留一个有价值的正式回归：`DecoderHabitContractTest` 新增“煮→的→面”成功分段提交一次、关闭重开数据库、原生缺少该整句时依然召回首位，且记录恰为一次。恢复原代码后上述 completion/util/state 集合共 30 个类、179 项测试全部通过，失败/错误/跳过均为 0，`BUILD SUCCESSFUL in 38s`，日志 `quality-restored.log`。

后续方案必须先补足两类依据：词条的普通表达/专名来源，以及原生真实选词来源。只允许高把握的冷门来源退出默认推荐，既有普通短句不因“小词库未收录”自动降级；实际学习证据优先。若来源识别不可得，则本轮不能声称“既不误伤又杜绝怪词”已经实现。本次实体手机未出现在 ADB，只有 emulator-5554；没有真机性能或原生旧习惯重启验收。


#### 原生旧习惯来源接口核对

补充只读审查确认：当前 `Rime.kt` / `CandidateListItem` 未提供候选来源，只有文字与注释。参考版本的 C API 候选结构同样未导出来源，不能把 reserved 当作可用用户词标志。原库虽导出 Menu、Service、UserDictManager 等 C++ 符号，现有 addon 原型只验证独立 translator 且关闭 user_dict，未证明现有 session 的来源兼容。

只识别候选 `type` 也不足：参考实现会把系统词补全和用户词补全都标为 `completion`。动态符号、字符串和打包配置中未找到现成 Lua filter 或用户词注释标记能力，不能用一行 schema 配置安全补上。

可靠方向是匹配定制源码，在生成/去重时保留明确用户来源并随现有候选快照导出；备选是原生 levers 只读导出用户词后建立缓存，必须另验实际库兼容、删除记录、读音映射及后台加载。二者均不应新增逐键数据库扫描，也不能把导出词条伪造为本机点击。已向用户询问定制库原始源码的其他仓库/目录，以便核对而非擅自替换原库。


### 2026-09-28 继续验证：不替换原库的旧习惯来源读取

本轮使用仓库原始 arm64 `libyuyanime.so`，哈希保持 `4c015d48b11033e8cda135c41099142b81b04151d5ff744319426e635f5a6a88`。仅在 emulator-5554 的自建 app_process/用户数据目录运行，没有安装 APK、没有访问实体手机或既有应用数据。原型、脚本、日志与结果位于本机 `artifacts/diagnostics/2026-09-28-daily-sentence/engine-eval/habit-export/`。

#### 可复现的新证据

1. **不能直接照搬上游 C API 表布局。** 原库在 RimeApi 中插入了方法；按公开 1.11.2 表访问 `find_module` 实际误调用 `RimeConfigGetCString`，隔离进程崩溃。符号和回溯记录在 `learn.log`。随后按本原库实际导出符号绑定参数为基础类型的函数，成功访问 levers 导出接口；没有依赖跨库 C++ 对象或 RTTI。此发现补充此前“有 C API 即可用”的判断，必须锁定库哈希/ABI。
2. **原生已学词可以读取。** 极小 schema 中真实选择“主峰”和“朱逢博”各一次，导出各 count=1；未选“珠峰”不在导出里，重开仍有两条。TSV来自原库学习，不经过应用 SQLite。
3. **实际词库及九宫格也验证了。** 使用项目 `pinyin.table.bin`、`pinyin.prism.bin`、`t9_pinyin.prism.bin` 与原库内嵌 T9 schema，数字 `9483364`（原生键 `WGTDDMG`）选“主峰”，`948336426`（`WGTDDMGAM`）选“朱逢博”；原生完整码排序在重启后保留主峰首位，来源导出保持两条各一次。数字 `948336` 的原生首屏仍是“羞愤”等，不能把原型的小型拼音补全结果推广为生产数字补全已改善。
4. **活跃库不可导出。** 引擎持有数据库时返回 -1。原型在独立测试进程关闭 session 后才成功，绝不授权在用户打字过程中关闭 session。
5. **OpenReadOnly 不等于文件完全不变。** 直接导出会更新 LevelDB 的 CURRENT、MANIFEST 和日志。采用全部写入者已关闭时的副本，再对副本初始化/导出，原始库所有文件前后 SHA256 相同。
6. **删除记录不会复活。** 在合成实验的原生学习库中删除“朱逢博”并重启后，副本导出仅剩“主峰”；生产配置和极小 schema 均验证。没有删除用户实际手机词条。

`run-production-probe.py` 使用全新模拟器目录完整复现“选择→重开→副本导出→删除→再次重开→副本导出”，自动校验并清理自己的目录。最新证据 `fresh-replay/result.json`：两次来源快照符合预期，原库哈希均相同，活跃导出失败得到识别。参考代码和最初失败记录均保留，不将实验 so 放入正式 APK。

#### 接入时仍必须遵守的边界

- 导出只提供词条/读音/计数及全局 tick，不完整提供个体权重和时间。它适合作为“原生已学”的资格证据，不能用来重建最近选择、替换原生排序或制造本机点击。
- 来源缓存需按成功快照原子替换，不能永久并集而复活已删记录；导出失败不得清空旧缓存或默认把个人词当成陌生词。
- 副本不能热拷贝。App 当前存在后台 `Launcher` 初始化及 `Rime.startup`/切换 schema 路径，接入前必须核对写入者关闭、初始化顺序和并发，不能在按键过程中调用 `cleanup_all_sessions` 或改变全局目录。
- 小库模拟器导出已经有几十至一百多毫秒，明确不能进入逐键/主线程；尚未测真实大库、实体手机、端到端按键、撤销和多音分段。
- 本轮结论是原库旧习惯来源读取原型可行，**不是候选过滤已修复，也不是 App 集成已完成**。正式生产代码/词库未修改，没有构建或安装修复 APK。
