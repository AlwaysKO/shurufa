# 微信关系画像与 AI 回复设计

日期：2026-09-11  
状态：已被“截图采集、后台统一分析”方案替代；AI 服务代码保留但采集端不触发

> 2026-09-11 需求调整：微信端不再依赖无障碍文字节点解析消息，也不在输入法内即时请求 AI。
> 当前实现仅识别会话标题和输入框、裁剪上传聊天区域截图。`DEEPSEEK_API_KEY` 暂不配置，
> OCR、双方消息还原、用户画像和回复生成将在后续后台批处理功能中统一完成。

## 目标与边界

在现有被动聊天采集、关系档案与零 Token 候选之上，补齐微信私聊/群聊的文字页面解析、关系画像训练和 DeepSeek 回复候选。系统只观察当前用户主动打开的可见聊天页，不滚动、不点击、不发送；候选被点击后只写入微信输入框。首版只处理微信可访问性树中置信度足够高的文字消息，不扩展 QQ、抖音、语音转写或图片理解。

## 方案

Android 使用保守的 `WeChatChatAdapter` 解析聊天标题、会话类型、文本气泡方向和群成员名。解析成功后既进入现有 Room outbox，也将当前会话身份与最新来信写入带过期时间的本地活动上下文。输入法仅在微信文字编辑器、空输入状态且上下文未过期时请求关系候选。

服务端增加版本化 AI 画像和 AI 调用记录。后台由用户手动点击“训练画像”，服务端从该会话双方最近的合格文字消息提取确定性统计和代表样本，再请求 DeepSeek 输出严格 JSON；成功校验后才生成新版本，失败不覆盖旧画像。回复请求只携带当前关系画像、最近少量对话、当前来信和历史零 Token 候选，不发送完整历史。

候选路由遵循现有文档：初始和第一次“换一批”只返回零 Token 候选；第二次起才允许 AI。DeepSeek 未配置、超时、返回非法 JSON、画像不存在或预算受限时静默回退。所有数据库查询都以 `user_id` 和完整会话身份隔离。

## 数据流与错误处理

`微信可见页 → WeChatChatAdapter → CaptureCoordinator → Room 上传 + ActiveChatContextStore → 输入法候选请求 → 服务端身份查询 → 零 Token/DeepSeek 路由 → 候选栏 → 用户点击填入`。

AI 密钥仅保存在服务端 `DEEPSEEK_API_KEY`；Android 和网页永远不接触密钥。服务端配置模型、超时、训练最少消息数及最大上下文条数。日志只记录调用状态、模型、耗时和 token 用量，不记录提示词或回复正文。AI 请求失败对输入法返回可用的历史候选及 `fallback_reason`，不暴露供应商错误。

## 测试

服务端用注入式假 AI Provider 验证画像样本包含双方且会话隔离、JSON 校验、版本写入、刷新阈值、回复与回退。Android 用脱敏的合成可访问性树验证私聊/群聊、方向、含糊页面跳过、当前上下文过期和 API DTO；候选点击只提交文字。最后运行服务端测试/构建、客户端测试/构建及 Android 相关单测/Debug 构建。
