# 私人关系型输入法设计

日期：2026-08-20  
状态：分阶段实现中；关系档案与零 Token 历史回复候选已完成服务端和后台阶段

## 当前实现进度（2026-08-24）

已实现：标准聊天消息与媒体模型、客户端/服务端双层去重、通用被动采集链路、关系档案后台维护，以及按“相同上下文 → 当前关系高频 → 同关系类型 → 用户通用”回退的零 Token 历史回复候选。候选只返回用户真实发送过的文本，不调用 AI；后台可以编辑关系类型、称呼、亲密度、玩笑尺度和备注，并预览候选及其来源。

尚未实现：微信、QQ、抖音真实页面适配器及真机验收、Android 当前关系可靠识别和候选栏接入、表情反击链、关系训练、DeepSeek 中转、JSON 导入与回滚、AI 成本路由。真实适配器完成前，Android 不请求关系候选，避免关系串台。

## 1. 产品定位

本项目不以复刻商业输入法为目标，而是构建一个能够逐渐学习使用者表达方式的私人输入系统。功能优先级为：

1. 像本人，理解不同关系中的表达差异；
2. 好玩，围绕专属梗、表情包和共同记忆形成关系玩法；
3. 高效，在不破坏原有输入体验的前提下提供补全和快捷能力。

产品核心不是单一的“用户人格”，而是关系记忆系统：同一个人在客户、朋友、家人、私聊和群聊中具有不同表达方式，候选内容必须由当前关系驱动。

## 2. 已确认的硬性原则

### 2.1 只观察，不代操作

- 支持微信、QQ、抖音的聊天上下文采集。
- 不主动打开应用、切换会话、点击控件、滚动页面或发送消息。
- 仅当用户正常打开或手动滚动聊天页面时，读取当前可见内容。
- 除首次启用输入法、无障碍和通知读取权限外，采集、去重、上传和学习不能要求手机端额外操作。
- 不显示采集 Toast，不振动，不使用干扰用户的悬浮提示，不抢占输入焦点。
- 页面结构或会话身份不明确时保守跳过，不能猜测归属。

### 2.2 规则和数据优先，AI 最后兜底

- 能通过历史检索、统计、规则、缓存和轻量算法解决的功能不得调用大模型。
- 首批智能回复候选不调用 AI。
- 第一次点击“换一批”仍不调用 AI。
- 第二次及以后才允许调用 AI，阈值由后台配置。
- AI 不可用、超时或预算不足时，静默回退到零 Token 候选。
- 关系训练只在后台手动触发，且累计新增消息达到配置阈值后才允许执行。

### 2.3 所有发送均由用户确认

- 输入法可以主动展示候选，但不能自动填写或自动发送。
- 点击文字候选只填入输入框，由用户决定是否发送。
- 图片和表情通过目标应用支持的富内容接口提交；不支持时降级，但不得自动跳转或操纵应用。

## 3. 总体架构

```text
微信 / QQ / 抖音
        ↓
被动感知层（无障碍节点、通知、窗口截图）
        ↓
标准消息层（会话、发送者、方向、类型、时间、资源）
        ↓
本地去重与低优先级上传
        ↓
服务端消息库、资源库、统计与关系记忆
        ↓
零 Token 候选路由 ──低置信度/第二次换一批──> AI 候选
        ↓
输入法自适应候选栏
```

微信、QQ、抖音分别实现版本化页面适配器，统一输出标准消息模型。单个适配器失效不能影响输入法或其他应用适配器。

## 4. 多模态消息采集

双方消息均采集，支持：

- 文本、Emoji、系统提示和撤回提示；
- 图片、静态表情和动态表情的当前可见帧；
- 视频封面、时长和可见描述；
- 语音时长及可见状态，不主动播放或读取音频；
- 链接标题、摘要、域名和缩略图；
- 文件名、类型和大小；
- 音乐、位置、联系人和小程序卡片；
- 红包、转账金额与状态（页面可见时）；
- 抖音视频卡片、作者、标题和封面。

无 Root 条件下不能保证取得应用内部原始媒体文件。图片和表情以窗口截图配合无障碍节点坐标裁剪，屏幕显示质量可以接受。若通知消息提供可访问的媒体 URI，可优先保存更高质量资源。

采集任务在滚动停止后合并触发，截图、裁剪、压缩、哈希和上传均不得运行在键盘主线程。快速滚动、低电量、发热、弱网或存储不足时允许跳过低价值任务。

## 5. 消息与资源去重

去重分为两个层次，避免“同一文件重复保存”和“真实重复发送被误删”混为一谈。

### 5.1 资源去重

- 使用 SHA-256 识别完全相同文件；
- 使用 pHash/dHash 识别压缩、缩放或轻微裁剪后的相似图片；
- 相同资源只保存一份实体文件；
- 相似资源可以建立聚类关系，但不自动删除。

### 5.2 消息去重

消息指纹至少包含：应用、会话、发送者、方向、消息类型、标准化内容、可见时间、页面顺序和相邻消息摘要。手机端维护已见缓存，服务端建立幂等事件约束。

同一个表情发送十次时，资源只保存一份，但十次消息行为全部保留。客户端重装或重复上报也不能生成重复事件。

## 6. 关系记忆系统

每个联系人和群聊拥有独立关系卡片，数据不足时按以下顺序回退：

```text
联系人或群聊专属模型
        ↓
关系类型模型（朋友、家人、客户等）
        ↓
用户通用表达模型
```

关系卡片包含：

- 关系类型、亲密度与可开玩笑尺度；
- 双方称呼、口头禅、Emoji 和表情偏好；
- 用户面对该关系时的句长、标点、语气词和回复媒介；
- 共同事件、专属梗、未结束话题和重要日期；
- 推荐表达、禁忌表达和典型真实回复；
- 关系变化、训练版本、置信度及证据引用。

系统默认给出“最像本人”的候选，同时提供简短、热情、幽默、抽象和认真等风格变体。

## 7. 零 Token 能力

日常功能优先由本地或服务端普通程序完成：

- 历史相似对话检索；
- 联系人专属高频回复；
- 表情包关键词、哈希和向量检索；
- 表情反击链：“对方发 A，用户通常回 B”；
- 联系人专属表情排序；
- 旧梗、称呼和历史原话召回；
- 表情接龙和回复媒介预测；
- 关系暗号和专属快捷短语；
- 聊天成就、关系时间线和历史回顾；
- 语言指纹、活跃时间和回复间隔统计；
- 已缓存 AI 结果复用和接受率排序。

功能分布以约 80% 直接服务键盘候选、20% 用于后台回顾分析为目标。

## 8. AI 成本路由

```text
L0 本地规则：去重、关键词、固定短语、表情匹配
L1 统计检索：高频回复、相似上下文、个人排序
L2 轻量算法：向量、简单意图和风格特征
L3 大模型：复杂回复、关系分析、潜台词和冲突救场
```

后台需要提供以下配置：

- `ai_trigger_after_refreshes`：换一批达到多少次后允许调用 AI，默认 2；
- 每日和每月 Token 上限；
- 单次候选数量、模型、超时与降级策略；
- 每个应用或关系是否允许自动触发；
- 关系训练所需最少新增消息数；
- 单次训练最大消息量。

AI 请求只携带精简关系卡片、最近少量上下文和必要证据，不重复发送完整历史。按关系、意图和上下文指纹缓存生成结果。

第一阶段 AI 能力包括：关系画像训练、深度分身回复、言外之意识别和冲突救场。图片语义分析暂不自动启用。

## 9. DeepSeek 网页版训练中转

付费 API 不是关系训练的必需条件。后台提供“AI 中转训练台”，通过确定性程序压缩消息，再由用户手动交给 DeepSeek 网页版分析。

程序压缩不调用 AI，负责：

- 删除重复、无信息和过度相似样本；
- 统计称呼、口头禅、Emoji、句长和回复时间；
- 选取高频、近期、反常和长对话代表样本；
- 为图片和表情编号，并生成联系表拼图；
- 在文本中用 `IMG-001` 等编号建立图文关联；
- 估算整理后的文本长度。

训练流程为：

1. 后台筛选达到新增消息阈值的关系；
2. 批量选择多个联系人或群聊；
3. 为每段关系生成互相隔离的分析包；
4. 复制提示词和图片拼图到 DeepSeek 网页版；
5. DeepSeek 按规定 JSON Schema 返回结果；
6. 将 JSON 粘贴回后台；
7. 后台校验、展示差异、保存并推进训练游标。

批量任务支持下载 ZIP。每个关系目录包含 `prompt.md`、`messages.txt`、`statistics.json` 和编号图片拼图。只有成功导入结果后才更新训练游标。

导入结果必须校验训练 ID、关系 ID、版本、字段、枚举、置信度和证据编号。支持历史版本查看与回滚，禁止一次错误结果直接覆盖原关系记忆。

## 10. 输入法交互

候选栏根据输入状态自动切换：

```text
正在输入拼音
→ 正常汉字候选

输入区为空且处于已识别聊天页面
→ 关系回复候选

对方刚发送图片或表情
→ 对应表情、旧梗和文字反应

非聊天应用
→ 常用短语、剪贴板和普通补全
```

候选示例：

```text
[像我：你又来了] [😂表情] [旧梗] [换一批 ↻]
```

AI 候选使用轻量标识区分，以便统计接受率。输入法记录直接采用、修改后采用和忽略，用于持续改进排序，但不得为此增加额外 AI 调用。

## 11. 无 AI 图片和表情分析

图片与表情默认只使用传统算法：

- 精确哈希与感知哈希；
- 尺寸、宽高比和颜色直方图；
- 发送人、会话、时间和使用次数统计；
- 前后文本关联；
- 人工关键词和分类；
- 双方常用表情排行与表情反击链。

不因采集到图片自动调用视觉模型。未来如增加图片语义分析，也必须由后台手动批量触发并预估成本。

## 12. 异常处理与降级

- 会话识别不明确：使用通用候选，不写关系记忆；
- 页面结构变化：停止对应适配器采集；
- 图片边界异常：跳过，不扩大截图范围猜测；
- 断网：进入有上限的本地队列，恢复后低优先级上传；
- 上传成功：删除手机临时裁剪文件；
- AI 超时或预算不足：返回零 Token 候选；
- AI JSON 无效或串关系：拒绝导入；
- 单个适配器故障：不得影响键盘输入和其他应用；
- 所有错误仅在后台状态页记录，手机端不弹出干扰提示。

核心原则是：采集遗漏可以以后补，关系串台和干扰用户不能发生。

## 13. 验证标准

### 13.1 采集与去重

- 同一页面反复滚动不会重复入库；
- 内容相同但时间、位置不同的真实消息不会误合并；
- 所有消息类型均有独立解析测试；
- 微信、QQ、抖音保存页面节点快照作为回归样本；
- 页面结构变化时保守停止；
- 自动检查代码不存在点击、滚动、手势注入和自动发送路径。

### 13.2 性能

- 键盘主交互新增延迟目标低于 10ms；
- 截图、裁剪、哈希和上传不运行在主线程；
- 快速滚动时合并事件，不逐帧截图；
- 低电量、发热、弱网和存储不足时自动降级；
- 长时间运行无 Bitmap、无障碍节点和队列泄漏；
- 采集过程不造成可见掉帧或界面变化。

### 13.3 AI 与训练

- 默认第二次换一批才允许调用 AI，修改阈值后生效；
- 预算不足时只返回零 Token 候选；
- 批量分析包关系隔离、编号稳定、支持增量生成；
- 错误 JSON、串关系结果和旧训练版本被拒绝；
- 关系卡片导入支持差异预览和回滚。

## 14. 建议实施顺序

1. 标准消息模型、会话身份与客户端/服务端幂等去重；
2. 微信被动文本采集，再扩展 QQ、抖音；
3. 图片、表情和其他多模态裁剪上传；
4. 零 Token 关系候选、历史回复和表情反击链；
5. 自适应候选栏与接受反馈闭环；
6. 关系记忆后台与批量 DeepSeek 分析包；
7. JSON 导入、差异预览、版本与回滚；
8. 第二次换一批后的可配置 AI 兜底；
9. 关系时间线、聊天考古、成就和其他娱乐玩法。

每一阶段都必须先证明不会影响原有输入体验，再扩展下一类采集或智能能力。
