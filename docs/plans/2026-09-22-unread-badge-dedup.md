# 未读数字变化的精确去重修复

沿用用户已确认的同会话同内容不重复保存方向，范围仅修复真机已确认的左上角未读数字造成额外截图；不改变图片内容、不正文OCR、不引入近似阈值、不修改数据库/上传协议。

## 根因与设计

- 原始PNG正文及输入栏完全相同，仅标题栏未读数字2912像素改变。整张WebP SHA改变，且有损编码会让解码正文产生少量差异。因此不能用有损文件解码后的正文精确SHA代替原图。
- 媒体处理在最终裁剪之后、编码之前，对完整正文区域逐行计算精确像素SHA（包括尺寸），仅持有摘要，不保留整张图或额外大Bitmap。区域由App布局适配提供，未知边界不生成键。
- 标题仍只运行既有标题OCR；基于实际选中的标题行框计算原始精确像素SHA，不把返回按钮/未读数字当作联系人名字，不修改姓名映射。
- 只对已确认的当前窗口/身份代次，在身份key、标题精确像素SHA、正文精确SHA全部相同时跳过保存。只缓存上一个成功保存内容；失败不更新，导航清空，未知标题/边界或未确认页不跳过。保存原图及原文件SHA，不改变后端附件协议。
- 通用哈希/同scope守卫不含微信文案；微信空树提供标题/正文区域布局。QQ/抖音已有可读视口使用真实聊天区，通知回退身份未确认，不能为了统一强行把未确认通知也用正文相同合并。

## 实施与验收

1. 原始区域哈希与守卫测试先红：数字变化正文key相同、正文一个像素变化key不同、同正文不同标题/身份/窗口不能跳过、导航/失败/缺字段不能跳过。
2. 接入媒体→标题解析→持久化前守卫，保存成功才记账；标题首次确认重放仍保留旧归属确认逻辑。
3. 用两份私有原始PNG走真实媒体管线验证：附件SHA不同但正文精确key相同，标题文字key相同；未展开与展开正文key不同。真实图片及本机专属测试仅ignored。
4. capture/service回归、只读审查、原签名打包/保留数据覆盖安装并核对SHA；运行验收另记录，不能因两张样本就宣布总体准确率、内存、滚动条去重全部完成。

## 接线与阶段验证

- 首轮10项测试中3项预期红（原始正文/标题摘要和确认scope守卫），接线轮12项中2项预期红（媒体尚未提供原始摘要、失败/确认重放未门控）。实现后12项定向及1项私有真实样本回放通过。
- 私有回放实际使用媒体管线处理三张原始PNG：带未读数的展开图、无未读数的展开图、未展开图。前两者文件SHA不同，但原始正文摘要与人工核对标题区域摘要一致；未展开与展开的正文摘要不同，守卫不跳过转写变化。标题区域为本机人工标注，此离线测试不冒充运行手机ML Kit；生产代码使用ML Kit实际选中标题行框。
- `pending→confirmed`重放不建立新去重缓存，避免使用第二帧标题与第一帧正文。首次完全相同文件快速路径也需已有可信同帧缓存才启用，防止永远被旧文件SHA短路而无法建立原始摘要缓存。保存失败不记录，旧scope迟到保存不恢复新scope状态。
