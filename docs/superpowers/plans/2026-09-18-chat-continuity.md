# 聊天采集连续归属与人工合并（已批准范围）

用户已批准四项：微信列表进入漏采、身份跨天稳定/待确认接续、人工合并及未来路由、刷新恢复选择。保留所有历史消息和附件，不执行真实合并/删除/部署。

## 实施顺序
1. 服务端：新增会话合并指向；源会话保留为映射、列表隐藏，事务迁移消息并展平指向。入库遵循映射且不覆盖目标名称。添加按ID解析接口（用于刷新、合并后跳转），目标检索分页。防跨手机/App、自合并/循环、并发入库和链式合并。删除目标时其归属映射一起清除，不影响未合并会话。
2. 前端：合并目标搜索/分页及自定义确认；按用户持久保存App及各App最后会话。刷新先恢复ID（不局限列表前100项），目标合并后跳转；网络错误不当作删除，切换上下文拒绝迟到结果。
3. Android：共享身份稳定器接入持久证据仓库，保存经确认的精确标题字形映射及连续页面学习的变化，不全局按名字模糊归并。同一次页面有效期内待确认使用稳定标识，可靠后接续确认；导航/锁屏清除临时证据，历史稳定映射不清除。
4. 微信列表触发：补全列表点击携带标题/时间、页面加载中的有限重试，截图/识别失败补采；仍需聊天页证据，禁止靠任意点击采集其他页面，禁止固定轮询或重复内容入库。
5. 测试先红后绿：服务端使用独立initdb实例并核验data_directory/database；前端使用渲染夹具；Android隔离build目录。运行相关回归与前后端构建、Android单测/APK构建，核验ko:ko归属，记录证据。

## 验收与限制
- 同一源标识合并后所有新消息路由目标；新出现且无证据关联的标识不擅自模糊归并。
- 不声称获得微信真实联系人ID；同名不同联系人不能仅凭名字合并。
- 真机由用户操作验收；不自动发送消息或安装APK。
- 在原工作区外科式修改并保存起始副本，不重置或覆盖并行未提交工作，不自行提交Git。
