# 九宫格“穿 / chuan”候选排序调查

日期：2026-09-16  
范围：初次针对用户微信截图只做调查；后续用户明确授权修正完整单音节排序，实施与验证见文末。用途提示的交互修复独立处理。

## 现象与边界

截图左侧已经列出 `chuan`，顶部却显示 `ai’tan`，候选为“哀叹、刺探、笔谈、碧桃、词坛……”。
用户反馈大多数词已可正常输入，要求先调研，避免为一个字破坏现有规则。

沿用 Vault《shurufa推荐交互与真机交付》中九宫格约束：不展示纯首字母扩写的过长词，不补写中间音节，保留合法混输；不能仅靠黑名单修补个例。项目当前实现还支持有条件的原生整句回退、末音节逐键补全及个人选词学习，不应退回旧版白名单。

## 源码可确认的原因

1. **这是一组真实重码，不是“穿”的拼音错误。**  
   `chuan`、`ai tan`、`ci tan`、`bi tan`、`bi tao` 的九键全码都是 `24826`。“哀叹”并非一定来自错误简拼，它也是完整合法的多音节解释。

2. **应用层会把完整单音节放进靠后的分段组。**  
   `OfflineT9Candidates.select` 用 `code in T9Spelling.completionCodes(reading)` 划分原生 whole / prefix。  
   `completionCodes` 本来用于“至少两个音节”的整词补全与跨码学习，单音节直接返回空集合。因此 `chuan` 即使精确覆盖全部五键，也进入 prefix。  
   当前五键排序是 `whole + exact + partial + publicWhole + nativeSentences + segmentPrefixes`，完整多字词会排在“穿”前面。这里把“单音节”与“只覆盖一部分输入的前缀”混在一起了。

3. **本地词库不能补救这一分组。**  
   `T9Lexicon.parse` 只接收含空格的多音节词；词库构建说明也明确选取 2–6 字词。真实词库有“哀叹、刺探、笔谈、碧桃、词坛”，而单字“穿”依赖原生候选。

4. **顶部拼音跟随重排后的首候选。**  
   `RimeEngine.updateCandidatesOrCommitText` 用首候选读音调用 `T9Spelling.preedit`。因此“哀叹”排到第一后出现 `ai’tan` 是现有显示链路的结果；仅把显示硬改成 `chuan` 会让文字候选与读音不一致。

源码调查能确认应用层存在上述降序机制；不能仅凭截图断言手机上的原生 Rime 第一候选是什么，也不能断言原生解码完全没有额外问题。

## 搜狗资料能证明什么

- [搜狗手机版官方使用帮助](https://shouji.sogou.com/bangzhu.php?cid=53&pid=5)介绍九键拼音候选及手动分词操作。
- [腾讯云搜狗输入法企业版九键说明](https://main.qcloudimg.com/raw/document/product/pdf/1655_81582_cn.pdf)说明按拼音规则组合候选。

这些公开资料没有披露“单音节永远优先”的内部排序算法。用户实测搜狗在这个场景更合理是本次体验依据；不能把推测包装成搜狗算法事实，也不引入其私有词库。

## 初次调查提出的最小后续方向（实施状态见文末）

优先区分“完整单音节精确覆盖全部按键”与“只覆盖前缀的单字”，只在候选排序入口验证完整单音节优先的效果，仍保留合法同码多字词供选择。

不应：
- 针对“穿”或 `24826` 写特殊分支；
- 禁止所有多音节、取消末字补全、扩大内部简拼；
- 直接修改 `completionCodes` 让单字通过，因为它同时影响学习共享、可信整词判断和原生整句回退；
- 只改顶部拼音，或把 `chuan` 前缀也当成已完整输入的 `chuang`。

后续至少覆盖：
- 完整单音节：`chuan / chuang / shuang / zhuang` 等，以及逐键输入、删除；
- 合法同码多字词仍可选，显式分词与左侧锁定拼音不被覆盖；
- 已有“充电宝”末字补全、“我饿了 / 真的吗”整句与个人学习顺序；
- `649439` 纯简拼长词、`284269` 中间音节扩写等原反例；
- 首屏与翻页一致、原生选词索引正确，不能只测显示文案；
- 若原生首批没有完整单音节，单纯重排首批不够，需要另查召回/分页，不能声称已修好。

## 本轮验证记录

本地 Robolectric 探针使用 APK 当前真实离线词库、清空的临时测试历史，注入受控原生候选（不是手机原生 Rime 实测）：

- 输入码：`24826`。
- 原生输入顺序特意将“穿”排第一：穿、哀叹、刺探、笔谈、碧桃、词坛、传、船。
- 应用层实际输出：哀叹、刺探、笔谈、碧桃、词坛、壁毯、笔谭、祠堂、**穿**、传、船。
- “穿”由原生索引 0 下移到第 9 位；原生索引映射仍为 0，说明不是字丢失，而是排序下沉。
- 顶部读音结果为 `ai'tan`，与截图一致。
- `T9Spelling.allows("24826", "穿", "chuan") == true`，但 whole 分组判定为 false；“哀叹”的两项判定均为 true。

因此即便原生本来把完整单音节排第一，应用层也会主动降级它。已确认的修正位置是排序分组，而不是放宽合法拼写或把所有多字词禁掉。

探针位于本机 `/tmp/shurufa-hint-tests/T9SingleSyllableInvestigationTest.kt`，测试报告位于 Android 模块的忽略目录 `yuyansdk/build/ai-hint-check/test-results/testOfflineDebugUnitTest/`。本机没有 ADB 设备，未验证真实 Rime 召回次序与搜狗同键序对照。

## 用途提示独立修复

原实现只在换输入目标时收起提示，同一输入框重复点击可能既不换目标也不移动光标。本轮在显示键盘请求、宿主点击兼容回调、输入视图 restart、选区回调里仅清理提示及其定时任务，不清空候选、不修改斗图开关或查询。

[Android 官方文档](https://developer.android.com/reference/android/inputmethodservice/InputMethodService#onViewClicked(boolean))说明 `onViewClicked` 自 API 29 弃用且自绘宿主不保证调用，因此不单独依赖它，另用显示请求/restart/选区回调覆盖；仍需微信真机验收。

新增四项回归先在旧实现全部失败，修复后全部通过：同框点击、重复显示请求、位置未变的选区回调、同一目标 restart；其中点击和 restart 同时断言保留既有查询。

测试期间发现工作区已有文案断言与资源不一致：旧测试期望“根据你输入的文字匹配表情。请先输入文字，再点击。”，当前资源仍是上轮确认的带“AI斗图”文案。本次不擅自覆盖该断言或更改文案，单独记录此已存在的不一致；定向验证不代表全量测试通过。


## 2026-09-16 用户授权后的排序修复

依据：用户在本调查后明确要求“修正完整单音节的排序分组”。

- 仅修改 `OfflineT9Candidates.select` 的数字码排序分组：从已通过原有校验的原生候选中，提取**一个汉字且读音全码精确等于当前输入**的候选，组成默认优先组；组内保留原生相对顺序及选择索引。
- 其余候选继续走既有 whole / exact / partial / prefix 顺序，同码多字词没有删除。个人学习仍在分组之后生效，反复选择“哀叹”仍可将其置顶。
- 不改 `T9Spelling.completionCodes`、拼写过滤、词库、Rime 解码、分页与整句回退。原先未走长数字码重排的短码/字母码/显式分词入口不扩展范围。
- `24826` 优先“穿／传／船”，不会将尚未完整输入的“窗”当作精确音节；继续输入到 `248264` 时“窗”才进入精确组。继续输入“穿衣”的编码后，“穿”不再被提升。

正式新增回归：`OfflineSingleSyllableRankingTest.kt`，覆盖六项：同码词保留和索引、窗/双/装、逐键输入与删除、继续输入多音节、学习后重开、显式分词/字母拼音分支。
旧实现已复现“哀叹先于穿”和“祠堂先于窗”；修复后新增六项全部通过。

- 使用本机临时 Gradle 初始化脚本隔离构建输出和测试源集，避免其他并行开发及无关测试影响；正式回归源文件已保存在项目 `src/test`，不是仅保留临时探针。
