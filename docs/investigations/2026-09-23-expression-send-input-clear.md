# 推荐图发送确认后清空输入调查

## 用户要求

用户在发送确认框点击“发送”后清空原输入，取消不清空。不能在选择图片或打开确认框时提前删字；发送期间改写文字或切换输入目标后不能删除新内容。

## 已核对的链路

- `InputView.prepareExpressionForSending` 记录原 InputConnection 和完整文字快照。只有 `Sent` 且连接、文字未变化时清空；`WechatSubmitted`、`AppSubmitted` 保留原文。
- `ExpressionContentSender.sendPrivateCommand` 对微信 GIF 使用既有私有命令。返回 true 只能确认文件 URI 已交接，所以返回 `WechatSubmitted`。微信稍后显示原生发送确认框。
- 当前工程没有 `onAppPrivateCommand` 的确认处理，也没有与本次图片交接关联的宿主确认/取消事件桥接。用户之后点击微信发送按钮不会再次进入 InputView 的清空路径。
- 窗口隐藏会清理输入法推荐状态，输入连接也可能重建。仅靠“键盘重新显示”无法区分发送与取消，更不能借此推断用户确认。
- 现有 `PassiveChatAccessibilityService` 接收点击与窗口事件，但现状只用于被动聊天采集。不能直接把聊天页任意“发送”文本当作本次推荐图的确认按钮。

## 已排除的修补方式

1. 把 `WechatSubmitted` 改成 `Sent`：会在确认之前删字，取消无法保留输入。
2. 打开图片先清空、取消后恢复：会改变草稿/组合状态，遇到输入连接重建、取消未知或新输入时可能丢字或覆盖新内容。
3. 延时清空或返回键盘即清空：没有确认依据，同样误伤取消。

## 待取得的具体证据

确认用户指的是哪一个 App 的确认框。当前 Mac 的 ADB 仅有 emulator-5554，模拟器未安装微信，未连接用户手机；本机也没有旧 WSL 中用于接收端分析的微信反编译文件。

如为微信原生确认框，需要用户在连接的手机上操作一次推荐图确认界面的“取消”和一次“发送”，助手只读取按钮/窗口元信息和生命周期，绝不替用户发消息。不读取聊天正文来猜发送结果。核对当前版本是否有可用确认回调；否则验证现有无障碍服务能否稳定识别本次确认弹框与实际按钮点击，再实施限定于该次交接的确认状态桥接。

## 验证标准

- 打开确认框、取消、返回、交接失败：原输入保留。
- 明确确认发送：只清理本次原输入一次。
- 旧回调、重复回调、超时、切换 App/会话、原文被改写：不删除新内容。
- 原 GIF 交付方式、格式及原签名保持，沿用既有发送测试，再补确认/取消/生命周期回归并打包。

本次仅调查并记录长期要求，尚未修改发送逻辑，不宣称问题已修复。

## 真机连接后的补充证据

2026-09-23 本次 Mac 已通过 USB 识别荣耀 ELI-AN00。微信 8.0.78 / versionCode 3180；已装输入法 20260922.18，当前选用本应用兼容 IME。`enabled_accessibility_services` 返回 null，无已启用无障碍服务。

已看到文件传输助手里的“发送到当前聊天”确认框，含取消/发送两个按钮。弹框阶段键盘隐藏、输入系统所服务的是 DecorView，而非原始文字编辑器。普通 `uiautomator dump` 只得到空树，不能据此编造按钮节点或回调。

从本次手机完整只读提取微信 APK，使用 Android SDK 自带 apkanalyzer 核对相关字节码，原件仅在忽略的 `.runtime/expression-send-confirm/`：

- `tt5.i.a`：仅从 Bundle 取 `EXP_PATH_URI`，委托 `hm.y0`，同步返回是否打开接收流程；没有接收结果回调参数。
- `com.tencent.mm.ui.chatting.component.hm.y0`：创建当前确认框，将取消/确认分别绑定 `km`、`lm`，显示弹框后立即返回交接状态。
- `km.a`：只关闭确认框。
- `lm.a`：走微信内部 GIF 表情或普通图片发送流程，再关闭确认框；未向调用输入法发送确认/取消通知。

因此原私有命令的返回值不足以实现“发送清空、取消保留”。已向用户说明需要通过无障碍识别明确的确认按钮，等待是否接受此依赖；在答复前不引入新权限依赖、不改成提前清空。尚未替用户操作任何发送、取消或设置开关。

用户随后已启用无障碍，进入代码阶段。新增确认状态及保护测试，详情见 [实施与验证记录](../plans/2026-09-23-expression-confirmation-clear.md)。当前为待安装核实的验证包，未把shell未观察到的点击编造成已取得的真机证据。

## 用户安装后的失败定位

用户通过 Android Studio 安装后反馈发送仍未清空。设备核对版本为 `20260923.15` / `2026092315`，更新时间 `2026-09-23 15:09:19`，本应用 IME 已选中，无障碍服务在 Bound services 中。

本机 `persist.log.tag=M` 屏蔽了默认调试输出；仅设置临时 `log.tag.ExpressionConfirm=D` 后，本应用日志可读取。不能将之前空日志当作没有执行代码的证据，也不必先改代码重新安装。

用户再次手动复现后读到 `editor_mismatch`、`event_32_pending_false`。证明快照和输入焦点节点均取得，但节点可编辑性、密码、包名、文字一致性的联合校验未通过，尚未进入确认监听状态。这是当前最早已证实的阻断点；具体属性待运行时只读检查，不据此直接放宽保护。

用户保持原输入框打开后，通过当前 debug 进程的只读 JDWP 检查证实：焦点节点属于微信且窗口为1963，但 `className=null`、`isEditable=false`、`text=null`、`isPassword=false`、`isAccessibilityDataSensitive=false`。`refresh()` 返回true，刷新后可编辑性及文字仍无效。与此同时输入法 `InputConnection.getExtractedText` 能取得文字快照。不能将节点不可编辑等同于宿主实际不能输入，也不能将此结果直接归因为 Android 敏感数据过滤；目前仅证实节点属性缺失。下一步观察明确按钮事件及原输入连接在弹框前后的有效性。

随后用户再次亲自点击推荐图、发送并返回输入框。在本应用 `capture` / `observe` 入口进行只读调试，记录枚举和布尔值，得到：

- 交接前文字快照可读取。
- 收到确认窗口2002的两次 `TYPE_WINDOW_STATE_CHANGED`，标签符合发送确认框；此时原连接已不能读取文字。
- 用户确认发送后收到原窗口1963的恢复事件，**本应用没有收到对应 `TYPE_VIEW_CLICKED` 发送事件**。此前shell观察不到点击的现象在实际服务入口得到重复验证。
- 回到输入框后，新的连接能读取与原快照一致的文字；连接对象已经改变，原连接持续失效。

结论：20260923.15在本机真机验证失败，有“节点内容缺失”和“明确发送点击未送达”两个独立阻断。不能仅删除 `isEditable` / 文字匹配判断，也不能改用确认窗口消失、连接恢复、文件读取次数或延时来猜测发送。保持原文，不以构造事件的单测通过宣称支持此机型。没有修改微信、替用户发送或执行清空动作。

当前私有命令没有已验证的确认回传，尚未找到能满足原交互的可靠替代方案。已向用户询问是否接受返回键盘后提供明确的“清空输入”按钮；这会多一次点击，属于方案变更，答复前不实施。诊断完成后断开临时调试器并恢复专用日志开关。
