# 短词简拼与固定长句补全调查

日期：2026-09-23。基线：`e33c924`，开始调查时工作区干净。调查阶段完成源码、实际资产检查和应用层受控复现，当时未修改正式算法、词库或 APK。用户随后确认“继续”，实施与验证记录见 [实施计划](../plans/2026-09-23-input-abbreviation-completion.md)；下文保留修复前证据。

## 结论

两个例子需要分别解决：`559 → 就可以 / 良口镇` 是多音节简拼召回；`feiliuzhix → 飞流直下三千尺` 是尚未上屏时的固定长句前缀补全。之前“只允许最后一个音节不完整”的规则误伤前者，也不能提供后者。只放开长词长度限制、只换显示字母或只补入这几个词，都不够。

截图中的 `j'j'w` 可由当前显示兜底函数直接复现；它不是证明数字 5 被错误地绑定成 j，而是在没有可用词语读音时，取每个数字键的代表字母显示。

## 当前源码证据

- `T9Lexicon.queryEntries`：数字码只允许完整拼音或最后一个音节截短。`match` 虽然能枚举内部首字母匹配，后续 `trailingOnly` 检查仍拒绝这些结果。每个词的全部音节都要消费输入，不支持省略尚未开始输入的后三个字。
- `T9Spelling.preedit/allows`：原生候选再次经过同样的末音节限制。因此即使原生提供“就可以”，应用层仍会删掉它。
- `CandidateSelection.appendNativePage`：后页同样检查 `T9Spelling.allows`；只改首屏或本地查词不能闭环。
- `T9PinYinUtils.displayPendingDigits`：无候选读音时，`559` 对应键代表 `JJW`，最终显示 `j'j'w`；这条路径只服务显示，不负责选词。
- `PublicPhraseIndex`：仅保存文字和偏移，提供 `contains(text)`。没有拼音、频率或按数字/拼音查询能力。它能保留原生已提供的词，不能独立补回原生没提供的词。
- `OfflineT9Candidates`：先拼写过滤、召回及分组，再按个人选择排序。已经被过滤掉的目标无法靠增加学习权重恢复。
- `RimeEngine`：标准全键与九宫格都接入本地候选，但全键本地匹配没有数字码的 `trailingOnly` 限制。全键仍缺跨越后续未输入音节的长句召回；本轮未取得全键原生现场候选，不能断言它与九宫格的误删机制完全相同。

文件均位于 `android/YuyanIme/yuyansdk/src/main/java/`：候选逻辑在 `com/yuyan/imemodule/data/completion/`，拼写与显示在 `com/yuyan/inputmethod/util/`。

## 方案比较

| 方案 | 收益 | 问题 | 建议 |
| --- | --- | --- | --- |
| 撤销内部简拼和长词过滤 | 改动表面上少 | 旧乱词重新出现；仍缺长句前缀召回 | 不采用 |
| 分开增加短词简拼与固定长句补全，统一匹配证据 | 对应本次缺口，复用现有引擎和个人学习 | 需要可查询索引、排序和提交链路共同适配 | 推荐第一阶段 |
| 重建原生引擎并接语言模型 | 可进一步改善未收录自然短句的生成和排序 | 影响大，需独立兼容与性能验证 | 第二阶段独立评估 |

## 推荐设计

### 1. 短词简拼从词条反查，不先固定为一串字母

对 `559` 查询候选词的音节首字母数字码，允许 `jky / 就可以`、`lkz / 良口镇` 等同码解释共同参与排序。保留原始 `559`，不要先猜成唯一的 `jky` 再搜索，也不要枚举所有字母排列。

第一阶段重点恢复三字整词的纯简拼。二字简拼与单音节冲突更密集，应单独评估再开放；四字以上纯简拼长词继续沿用原有禁止规则。已有全拼和末音节补全保留。内部混拼不借此无条件放开，既有 `284269` 和 `649439` 反例继续单独验证。

词库索引必须包含真实读音和来源权重，常用口语、低频地名及个人明确选择分开评估排序。“就可以”目标为冷启动首屏、优先争取前 3；“良口镇”应可检索到，但不能因公开词库收录就与常用口语享有相同优先级。词频来自不同语料时需要校准，不能直接比较各库原始数字。

### 2. 固定长句有独立的前缀补全通道

将 `fei liu zhi x` 与“飞流直下三千尺”的前缀对齐，允许从已收录固定表达补出剩余文字。全键和对应九宫格数字码均支持；拼音行显示用户实际输入的 `fei'liu'zhi'x`，候选显示完整句子。

从常用固定表达和用户明确保存/选择过的长句开始，不把全部 185 万文字成员都视为高置信度预测句。初始实验可以采用“至少三个完整音节，再加下一音节前缀”的触发条件、每次最多 1–2 个长句建议；这是待验证参数，不能未经语料评估变成新的全局硬门槛。

排序同时看前缀匹配、词条可靠性、补出长度、同码竞争和个人选择。保留“飞流直下”作为可选项，保证用户只想输入前四字时仍方便选择。短输入 `fei` 不能被大量长句占满；继续输入与目标不一致时要立即撤回该补全，退格后按当前输入重新计算。

### 3. 匹配结果需要带依据，供首屏、翻页、显示和学习共用

当前候选只有文字、读音与原生索引，不足以区分完整词、纯简拼和未输入后缀的长句补全。建议增加最小的匹配描述：匹配类型、实际消费的按键范围、各音节已输入部分、未输入后缀范围，以及候选来源。

首屏和翻页用同一匹配结果判定资格，显示读匹配结果，不再用旧的“只缺最后音节”谓词把新候选二次过滤。候选提升后，`559` 的拼音行可随首候选显示 `j'k'y`；切换首候选为地名时可显示 `l'k'z`。这是候选读音解释，不改变按键记录或自动锁音。

只有明确选择并成功上屏才学习。用户用 `559` 选择“就可以”，记录真实短码选择及确定读音，不把次数复制到所有简拼组合；完整码选择可作为同词偏好证据，但不能伪造短码点击。点击固定长句补全时须正确消费实际输入，不能吞掉后来追加的按键；原生候选保留原索引及原生提交路径。锁音、分段状态先尊重用户约束，不直接插入不兼容候选。

### 4. 索引和性能

预构建简拼数字码和固定表达前缀索引，按前缀有界检索并缓存逐键状态；不在每次按键时遍历全部公开词条或把百万词条全部解析到 JVM 堆。复用锁定的原始词库来源，不逐例硬编码目标词。

记录冷加载、逐键查询 P50/P95、内存及 APK 增量。数值以同一真机上的现有版本为基线测量后确定，不用桌面 JVM 时间承诺手机不卡顿。新索引损坏/不可用时保留既有输入路径。

## 实施次序与验收方法

1. 固化新旧需求的测试矩阵，分别标记“未召回、被过滤、排名靠后、显示错误”。本次两个例子之外，增加未用于调参的常用三字短词和固定诗句；同时保留原乱词反例。验证：旧实现应在新增目标上失败，已有保护仍通过。
2. 先实现三字纯简拼的召回、匹配依据、显示和真实选择学习。验证：冷启动 `559` 可选“就可以”，地名可达；同码竞争、首屏/翻页、连续输入/退格、分段、锁音、重启学习均检查。
3. 增加固定长句前缀索引，覆盖全键和九宫格。验证：`feiliuzhix` 和 `3345489449` 都在首屏出现完整诗句；更短输入不过度补句，追加不匹配字母后消失，点短候选仍正常。
4. 跑现有公开语料 305 条和长句逐键快照 16 条，并加新增留出集、随机短码与人工检查。验证：统计目标首屏率、排名、坏候选占比、原正确首选退化，不把总召回增加直接说成体验提升。静态回放与真实按键测试分开报告。
5. 源码验证后按项目签名和 APK 规则打包，再由用户在反馈手机上验收实际输入体验。当前研究阶段不打包或安装；本机是 macOS，不能声称已复制到既定 Windows E 盘。

本阶段应修订的是“所有内部简拼一律拒绝”对可信短词的误伤，并新增固定长句补全能力；不撤销用户此前对纯简拼长词、任意乱拼和错误提交的约束。任意自然短句的语义质量属于后续引擎评估，不能用本次三个词能出现来宣称整体达到搜狗效果。
